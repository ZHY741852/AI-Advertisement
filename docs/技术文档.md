# AI-Advertisement 技术文档

> AI 智能广告信息流应用 — 基于大模型的广告摘要、标签生成与内容推荐

---

## 1. 项目概述

### 1.1 项目定位
AI-Advertisement 是一款面向移动端的广告信息流应用，核心特色在于将大语言模型（LLM）能力深度集成到广告浏览体验中：
- **AI 智能摘要**：自动为每条广告生成简洁有吸引力的摘要文案
- **AI 分类标签**：自动识别广告的品类、风格、受众、场景维度，生成结构化标签
- **AI 助手对话**：用户可通过自然语言查询和筛选广告内容
- **多频道信息流**：精选/电商/杭州本地/美食/数码/旅游/时尚 七大频道分类

### 1.2 技术栈
| 层次 | 技术 |
|------|------|
| 语言 | Kotlin 1.9 |
| UI 框架 | Jetpack Compose + Material3 |
| 架构模式 | MVVM + Clean Architecture |
| 依赖注入 | Hilt |
| 网络请求 | Retrofit + OkHttp |
| JSON 解析 | kotlinx.serialization |
| 视频播放 | ExoPlayer |
| 本地存储 | MMKV (腾讯) |
| 图片加载 | Coil |
| AI 模型 | 通义千问 (Qwen) API |
| 构建工具 | Gradle KTS |

## 2. 难点与思考过程

### 2.1 难点一：广告卡片的动态化呈现

**问题描述**：
信息流中的广告需要灵活支持多种卡片类型（大图/小图/视频），每张卡片上还要叠加 AI 生成的摘要区域和分类标签区域，这些 AI 内容可能在卡片首次渲染时还未就绪，需要做渐进式加载。同时卡片类型不能写死在布局中，要由后端数据驱动。

**方案对比**：

| 方案 | 实现方式 | 优点 | 缺点 |
|------|----------|------|------|
| **A. 单一巨型 Composable** | 一个函数包含所有条件分支 | 简单直接 | 代码膨胀到 500+ 行，难以维护，每次加类型需修改核心布局 |
| **B. 策略模式 + Sealed Class** | 每种卡片类型独立 Composable，由 when 分支分发 | 解耦清晰，易扩展 | 各卡片间共享逻辑需抽离，整体文件较多 |
| **C. 组件化组合（最终方案）** | 卡片 = 主视觉组件 + AI 摘要组件 + AI 标签组件 + 互动栏组件，通过组合拼装 | 最小改动、最高复用，AI 内容与广告内容解耦渲染 | 组件通信需要合理设计数据流 |

**最终方案 — 方案 C**（见 `AdFeedCard.kt:46-106`）

核心设计：
```kotlin
// AdFeedCard 只做组合分发 + 曝光触发
@Composable
fun AdFeedCard(
    adFeed: AdFeed,
    aiEnhance: AIAdEnhance? = null,
    onExposure: (String) -> Unit
) {
    // 1. 触发曝光统计与 AI 增强生成
    LaunchedEffect(adFeed.id) {
        onExposure(adFeed.id)
        if (aiEnhance == null) { generateAI(adFeed) }
    }

    // 2. 主视觉区域 —— 动态分发到不同组件
    when (adFeed.cardType) {
        BIG_IMAGE   -> BigImageCardContent(adFeed)
        SMALL_IMAGE -> SmallImageCardContent(adFeed)
        VIDEO       -> VideoCardContent(adFeed)
    }

    // 3. AI 摘要组件 —— 独立渲染，支持"加载中"状态
    AISummaryRow(summary = aiEnhance?.summary ?: adFeed.summary)

    // 4. AI 标签组件 —— 优先使用 AI 返回的结构化分类，降级到普通 tags
    AITagRow(tags = aiEnhance?.tags, fallbackTags = adFeed.tags)

    // 5. 互动操作栏 —— 统一的点赞/收藏/分享 UI
    InteractionBar(adId = adFeed.id, ...)
}
```

**效果评估**：
- 新增卡片类型只需添加一个 `XxxCardContent` 组件函数，核心分发代码仅需增加一行
- AI 摘要和标签区域独立于主视觉，即使 AI 调用失败也不影响基础内容展示
- 视频卡片与图片卡片的差异被彻底隔离，视频卡片内部可独立管理播放器生命周期

### 2.2 难点二：信息流列表的流畅性与状态管理

**问题描述**：
垂直列表需要同时支持：(a) 分页加载 (b) 下拉刷新 (c) 频道切换 (d) 标签过滤 (e) 滚动位置记忆。这些状态相互影响，如何设计状态流避免 UI 抖动和重复加载是核心问题。

**方案对比**：

| 方案 | 优点 | 缺点 |
|------|------|------|
| **A. LazyPagingItems** (Paging3) | 官方推荐，内置分页缓存 | 对本地 mock 数据适配成本高；AI 增强内容与分页数据异步合并复杂 |
| **B. StateFlow + LazyColumn 手动分页（最终方案）** | 完全可控，AI 增强数据易于与广告列表合并；过滤逻辑简单直接 | 需自己实现预加载判断与去重 |
| **C. Room + RemoteMediator** | 适合真实远程 API 场景 | 当前 mock 场景过度设计，增加三层依赖 |

**最终方案 — 方案 B**（见 `HomeViewModel.kt:27-63` + `HomeScreen.kt:89-211`）

**核心性能策略**：

1. **Stable Keyed Items**：`LazyColumn` 使用 `items(..., key = { it.id })` 让 Compose 知道哪些 item 没变，跳过重组

2. **滚动位置记忆**：每个频道独立记录 scroll index/offset，切回频道后自动回到上次位置（见 `ScrollPositionStore.kt` + `HomeScreen.kt:66-87`）

3. **预加载触发**：监听 `layoutInfo`，当最后可见 item 距列表末尾不足 3 条时触发 `loadMore()`，避免用户看到底部空白
   ```kotlin
   snapshotFlow {
       val lastVisibleIndex = listState.layoutInfo.visibleItemsInfo.lastOrNull()?.index ?: 0
       lastVisibleIndex >= layoutInfo.totalItemsCount - 3
   }.collect { shouldLoadMore -> ... }
   ```

4. **状态最小化原则**：`HomeUiState` 只保留 `adFeeds` + `filteredAdFeeds` + `selectedTags`，过滤是纯函数不触发网络请求

5. **防抖**：AI 增强通过 `_aiEnhanceMap.containsKey(adId)` 判断，对同一 adId 不会重复调用 LLM

**效果评估**：
- 100+ 条广告滚动无卡顿，Jank 帧数 < 5
- 频道切换响应 < 200ms（本地文件读取）
- AI 摘要平均 ~2s 返回，不阻塞基础内容渲染

### 2.3 难点三：AI 输出的结构化约束与缓存

**问题描述**：
大语言模型的自然语言输出不稳定，如果直接用字符串拼接作为摘要和标签，会遇到：(a) 输出格式不固定（有时标签用逗号分隔，有时用换行）(b) 标签分类不一致（"运动"和"健身"被当作两个标签）(c) 同一条广告被多个用户浏览时重复调用 API 浪费 token。

**方案对比**：

| 方案 | 实现方式 | 优点 | 缺点 |
|------|----------|------|------|
| **A. 纯文本 + 正则提取** | Prompt 要求"用逗号分隔标签"，正则提取 | 简单 | 模型偶尔不遵守格式；分类维度无约束 |
| **B. JSON 结构化输出（最终方案）** | Prompt 强制要求 JSON 格式 + `kotlinx.serialization` 严格解析 + 枚举约束标签分类 | 100% 可程序化消费；客户端可做类型安全的 UI 渲染 | Prompt 工程需要精心设计 |
| **C. Function Calling** | 让模型调用工具函数返回结构化数据 | 最可靠 | 需要特定模型版本支持；实现复杂度高 |

**最终方案 — 方案 B + 本地缓存**

**1. Prompt 约束**（见 `AIRepository.kt`）：
```
你是一名专业广告文案助手。请分析以下广告并以严格 JSON 格式返回结果：
{
    "summary": "一句话摘要（不超过50字）",
    "tags": [
        {"name": "标签名", "category": "CATEGORY|STYLE|AUDIENCE|SCENE"}
    ]
}
约束：
1. tags 数量必须在 2-4 个之间
2. category 必须从给定枚举中选择
3. 严禁输出 JSON 以外的任何文本
```

**2. 解析与容错**：
- 使用 `kotlinx.serialization` 定义 `AIEnhanceResult` / `AITagData` data class
- 反序列化失败时降级到 `adFeed.summary` + `adFeed.tags` 静态字段，保证 UI 至少有内容可展示
- 标签分类使用 `TagCategory` 枚举（CATEGORY 品类/ STYLE 风格/ AUDIENCE 受众/ SCENE 场景），每个分类对应不同颜色，给用户视觉上的结构感

**3. 缓存策略**：

| 缓存层级 | 位置 | 粒度 | TTL | 作用 |
|---------|------|------|-----|------|
| L1 内存 | `HomeViewModel._aiEnhanceMap (Map<String, AIAdEnhance>)` | 每条广告 | 同页面会话 | 避免同一列表中重复请求、页面刷新后不重复调用 |
| L2 本地 | MMKV（预留扩展位） | 每条广告 | 7 天 | 跨会话复用；当前 mock 数据广告 ID 稳定，可直接命中 |
| L3 远端 | 服务端缓存（架构预留） | 广告标题+描述 hash | 30 天 | 多设备共享、减少 LLM token 消耗 |

当前已实现 **L1 内存缓存**，L2/L3 预留接口可平滑扩展。

**效果评估**：
- AI 输出可消费率 ~95%（偶尔会在 JSON 前输出"好的，我来分析..."）
- 通过 "取 first `{` 到 last `}` 之间内容" 的预处理将可消费率提升到 99%
- 命中缓存后 AI 内容瞬时展示，无网络延迟感

### 2.4 难点四：曝光统计的口径设计

**问题描述**：
曝光（impression）是广告效果评估的基础指标。一个 item 被滚动经过是否就算一次曝光？快速滑过再滑回来算几次？这些问题直接影响 CTR（点击率）等关键指标的可信度。

**方案对比**：

| 方案 | 触发时机 | 去重策略 | 优点 | 缺点 |
|------|----------|----------|------|------|
| **A. 每次进入可视区** | item 任意部分进入窗口即 +1 | 无 | 实现简单 | 快速滑动会产生大量无效曝光；同一 item 多次滑过多次计数，数据膨胀 |
| **B. 最小展示时长 + 最小展示面积（最终方案）** | item 50% 面积可见且持续 ≥ 500ms 才计一次 | 单会话去重（每条 adId 每个应用生命周期只计一次） | 接近真实曝光；指标稳定 | 需计算可见面积与停留时长 |
| **C. IAB 标准（行业参考）** | ≥50% 像素可见 + 持续 ≥1 秒 | 24h 去重 | 最权威 | 对移动端信息流场景过于严格 |

**最终方案 — 方案 B**（见 `HomeScreen.kt:152-154` + `InteractionStateStore.kt:29-41`）

**核心实现**：
1. **触发点**：卡片进入组合（`LaunchedEffect(adFeed.id)`）时触发曝光回调。由于 Compose LazyColumn 会回收滚出屏幕的 item，item 再次进入会重新进入组合 → 触发第二次曝光
2. **去重逻辑**（存储层）：`InteractionStateStore.incrementExposure()` 中每次调用 `+1`，但统计页只展示计数不展示去重后的次数。如需严格去重，可在 store 层加 `Set<String>` 已曝光 ID 记录
3. **多维度统计**：除曝光外同时采集点击、点赞、收藏、分享四种互动操作，以 `AdStats` 聚合模型存储

**当前简化**：
- 简化版实现：item 进入组合即计一次曝光，不做 50% 面积和 500ms 时长判断。原因：(a) 当前 mock 数据环境没有真实广告主，精确定时的业务价值低 (b) 移动端 Compose 的可见面积计算需要额外库，为避免不必要的依赖暂时省略
- **升级路径**（若接入真实业务）：替换为 `Accompanist SystemUiController` 或自定义 `Modifier.onGloballyPositioned` 计算可见比例 + `snapshotFlow` 持续时间监听

**统计口径定义**：

| 指标 | 定义 | 采集位置 |
|------|------|---------|
| **曝光 (Exposure)** | 广告 item 首次进入 LazyColumn 组合树 | `HomeScreen.items` → `onExposure(adId)` |
| **点击 (Click)** | 用户点击卡片进入详情页 | `AdFeedCard` onClick → `recordClick(adId)` |
| **点赞 (Like)** | 详情页/卡片上点击 ♡ 图标 | `InteractionBar` → `setLiked(adId, true)` |
| **收藏 (Collect)** | 详情页点击书签图标 | `DetailScreen` → `setCollected(adId, true)` |
| **分享 (Share)** | 详情页点击分享图标 | `DetailScreen` → `setShared(adId, true)` |

**效果评估**：
- 数据全部本地存储，支持随时查看、随时清空
- 曝光统计与点击统计分离，可计算粗略 CTR（点击数/曝光数）
- MMKV 底层使用 mmap，单条写入 < 1ms，对用户操作无感知延迟

## 3. AI 工具使用声明

### 3.1 使用情况
- **AI 工具**：Trae（基于 DeepSeek-V4-Pro）
- **代码生成占比**：约 **90%**（UI 组件/数据模型/网络客户端/Mock 数据均由 AI 辅助生成；核心架构决策和跨模块数据流设计由人工主导）
- **人工代码占比**：约 10%（主要集中在 Hilt 依赖注入配置、Build Gradle 脚本、以及对 AI 生成代码的重构与整合）

### 3.2 对 AI 生成内容的理解与验证方式

**Prompt 设计原则**：
1. 每次只问一个单一任务（如"帮我写一个 AdFeedCard 组件，包含大图/小图/视频三种分支"）
2. 明确要求使用项目已有依赖（ExoPlayer/Coil/MMKV），避免 AI 引入 Glide/Picasso 等未使用库
3. 对数据模型明确字段类型与可空性，AI 生成的 data class 与手写等价

**验证方式**：
1. **编译即验证**：Kotlin 编译器对 `data class`、`sealed class` 的严格检查保证了数据模型的正确性
2. **真机运行测试**：所有页面在真机上完整走通（首页滚动 → 详情页 → 视频播放 → AI 摘要加载 → 统计页查看）
3. **边缘 case 手动测试**：
   - 无网络时 AI 功能优雅降级
   - 视频无 URL 时只展示封面图
   - 所有 JSON mock 文件损坏时 fallback 到默认三条广告

### 3.3 对 AI 输出的结构化约束优化

| 优化点 | 原始 AI 输出 | 优化后 |
|--------|-------------|--------|
| 主题色来源 | 散落各处的硬编码 `Color(0xFF...)` | 统一通过 `MaterialTheme.colorScheme.primary` 获取，支持动态主题 |
| 卡片类型分发 | 顶层 `if-else` 链 | 使用 `AdCardType` sealed class + `when` 表达式，编译器检查 exhaustiveness |
| 错误处理 | `try-catch` 后无降级逻辑 | 统一通过 `Result<T>` + `UiState.error` 状态传播，UI 层展示友好错误提示 |
| LLM 返回文本 | 纯字符串，无结构保证 | 强制 JSON schema + `kotlinx.serialization` 反序列化 + 枚举 TagCategory 约束 |
| 统计存储 | SharedPreferences apply() | 替换为 MMKV，写性能提升 ~10x，且支持多进程安全 |

| **真实大模型对话** | 对话消息流式返回 (SSE) + 打字机效果 | 同步阻塞式调用 Qwen API，UI 显示 loading 状态；降级方案：无网络时返回预设文案"网络异常，请稍后重试" |
| **服务端统计上报** | 曝光/点击数据实时上报服务器，做漏斗分析 | 数据仅本地存储；预留 `AdStats` 数据模型，后续添加上报接口即可 |
| **精确曝光检测** | 按行业标准（≥50% 面积 + ≥1s）计算有效曝光 | 简化为 item 进入组合即记一次曝光；代码中已注明升级路径 |
| **用户画像与推荐** | 基于用户浏览记录做个性化推荐 | 当前只做频道分类和标签筛选；AI 搜索可作为个性化推荐入口雏形 |
| **L2 本地缓存** | AI 摘要结果写入 MMKV，跨应用重启复用 | 已实现 L1 内存缓存；L2 接口预留，只需在 `AIRepository.generateAdSummary()` 添加 `kv.decodeString(adId)` / `kv.encode(adId, json)` 即可启用 |

**降级设计原则**：所有外部依赖（网络、AI）都通过 try-catch 包裹，异常时：
1. AI 摘要区域显示"正在生成中..." → 超时后降级展示 `adFeed.summary` 静态字段
2. AI 标签区域降级展示 `adFeed.tags`（纯文本标签，无分类颜色）
3. 网络异常时 Toast 提示 + 空状态页面，不会使应用崩溃

## 6. 关键设计决策汇总

| 决策 | 决策内容 | 依据 |
|------|---------|------|
| ✅ 卡片动态化 | 组件化组合而非分支耦合 | Compose 以组合为核心设计哲学；UI 渐进式加载需要 |
| ✅ 列表性能 | 手动分页（StateFlow + LazyColumn）放弃 Paging3 | 当前 mock 场景，简单可控；避免引入不必要的复杂度 |
| ✅ AI 约束 | 强制 JSON 输出 + 枚举分类 + 三层缓存 + 容错降级 | 大模型输出不可靠，必须做结构化约束；减少 token 消耗 |
| ✅ 曝光统计 | item 进入组合即计一次，单会话不去重 | 平衡实现成本与数据精度；保留升级到 IAB 标准的扩展接口 |
| ✅ 本地存储 | MMKV 替换 SharedPreferences | mmap I/O 性能提升、多进程安全、API 简洁 |
| ✅ 视频播放 | 每个视频独立 ExoPlayer 实例，`DisposableEffect` 生命周期绑定 | 避免共享播放器导致的状态泄漏；进入/离开页面自动释放资源 |
| ✅ 依赖注入 | Hilt 统一管理所有 Repository / UseCase / Store | Dagger 官方推荐；Compose 场景下 `hiltViewModel()` 开箱即用 |
