# AI-Advertisement 技术设计文档

## 1. 项目概述

### 1.1 项目简介
AI-Advertisement 是一款基于 Jetpack Compose 开发的现代化广告信息流 Android 应用，集成通义千问大语言模型，提供 AI 智能摘要、AI 推荐标签、AI 对话助手等智能功能。应用支持多频道广告展示、视频播放、标签筛选、用户互动记录等功能。

### 1.2 目标用户
- 移动互联网用户
- 需要浏览各类广告内容的消费者
- 关注 AI 智能推荐体验的用户

### 1.3 核心功能
| 功能模块 | 功能描述 |
|---------|---------|
| 广告信息流 | 多频道广告展示，支持大图、小图、视频三种卡片类型 |
| 频道切换 | 精选、电商、杭州本地、美食、数码、旅游、时尚 7 个频道 |
| AI 智能摘要 | 使用通义千问大模型为每条广告生成智能摘要文本 |
| AI 推荐标签 | 自动生成分类、风格、受众、场景四类智能标签 |
| 标签筛选 | 基于标签的广告内容过滤功能 |
| 用户互动 | 点赞、收藏、分享、点击、曝光记录 |
| 视频播放 | 内置 ExoPlayer 视频播放器 |
| AI 对话助手 | 集成通义千问聊天能力，提供智能对话服务 |
| 数据统计 | 展示广告互动数据、曝光量、点击量等 |
| 滚动位置记忆 | 每个频道独立记忆滚动位置，提升用户体验 |

### 2.3 分层职责说明

#### 2.3.1 UI Layer (表现层)
- **Screens**：各功能页面，包含 HomeScreen、ChatScreen、DetailScreen、SearchScreen、StatsScreen
- **ViewModels**：管理页面状态，处理用户交互逻辑，通过 StateFlow 暴露 UI 状态
- **Components**：可复用 UI 组件，如 AdFeedCard、VideoPlayer、CachedImage、InteractionBar 等

#### 2.3.2 Domain Layer (领域层)
- **Models**：核心业务数据模型，如 AdFeed、AdChannel、AdCardType
- **UseCases**：独立业务用例，每个用例处理一个具体业务逻辑
- **Repository Interfaces**：定义数据访问契约，不依赖具体实现

#### 2.3.3 Data Layer (数据层)
- **DTOs**：网络/本地数据传输对象，与具体数据格式耦合
- **Mappers**：DTO 到 Domain Model 的转换逻辑
- **Repository Impl**：Repository 接口的具体实现
- **Mock Data Provider**：本地 JSON 模拟数据提供者
- **AI Client**：通义千问 API 客户端封装

#### 2.3.4 Core Layer (核心层)
- **Common**：通用工具，如 Result、UiState 类型
- **Exception**：异常处理与错误定义
- **Network**：网络拦截器、API 服务定义
- **Storage**：本地持久化存储封装（MMKV）
- **AI Model**：AI 相关配置与数据模型
- **Image**：Coil 图片加载配置

#### 3.2.2 AI 调用流程设计

```
触发条件: 广告卡片首次渲染时（LaunchedEffect）
    │
    └─► HomeViewModel.generateAIEnhance(adFeed)
         │
         ├─► 检查缓存 Map：若已存在则跳过
         │
         └─► GenerateAdSummaryUseCase(title, description)
              │
              └─► AIRepository.generateAdSummary()
                   │
                   ├─► 构造 Prompt: System Prompt + 用户 Prompt（广告标题+描述）
                   │
                   ├─► QwenService.chatCompletion(ChatCompletionRequest)
                   │    └─► Retrofit 发起 POST → 通义千问 API
                   │         ├─► HeaderInterceptor 添加 Authorization: Bearer API_KEY
                   │         └─► LoggingInterceptor 记录请求日志
                   │
                   ├─► 解析返回结果：
                   │    ├─► 提取 choices[0].message.content
                   │    ├─► 去除 ```json 包裹标记
                   │    └─► kotlinx-serialization 解析为 AIEnhanceResult
                   │
                   ├─► 成功：转换为 AIAdEnhance(summary, tags)
                   │    └─► 更新 aiEnhanceMap → UI 自动刷新
                   │
                   └─► 失败（网络异常/解析失败/API 错误）：
                        └─► 生成 fallback 摘要（截取前 50 字）
                             + fallback 标签（4 个兜底分类标签）
```

#### 3.2.3 AI 调用优化策略

1. **懒加载触发**：仅在卡片首次渲染时调用，避免重复请求
2. **内存缓存**：通过 `Map<String, AIAdEnhance>` 缓存已生成结果
3. **容错降级**：AI 失败时自动使用本地 fallback，不影响用户体验
4. **静默失败**：catch 所有异常，不显示错误提示，保证流畅体验
5. **异步执行**：通过 viewModelScope.launch 异步执行，不阻塞 UI

### 3.3 视频播放模块

#### 3.3.1 视频播放组件设计

```kotlin
@Composable
fun ThumbnailVideoPlayer(
    videoUrl: String,
    thumbnailUrl: String?,
    modifier: Modifier = Modifier,
    autoPlay: Boolean = true,
    useController: Boolean = true
) {
    // key = videoUrl: 保证 URL 变化时重建播放器实例
    // 避免不同视频卡片复用同一个 ExoPlayer 实例
    var player: ExoPlayer? by remember(videoUrl) { mutableStateOf(null) }

    // URL 合法性检查
    val hasValidUrl = videoUrl.isNotBlank()
        && android.net.Uri.parse(videoUrl).scheme != null

    if (hasValidUrl) {
        // URL 有效：创建播放器 + 渲染 AndroidView
        DisposableEffect(videoUrl) {
            val exoPlayer = ExoPlayer.Builder(context).build()
                .apply {
                    setMediaItem(MediaItem.fromUri(videoUrl))
                    prepare()
                    playWhenReady = autoPlay
                }
            player = exoPlayer
            onDispose { exoPlayer.release() }  // 组件销毁时释放资源
        }
        AndroidView(...) { playerView ->
            playerView.player = player
        }
    } else {
        // URL 无效：降级显示缩略图
        if (thumbnailUrl != null) {
            CachedImage(imageUrl = thumbnailUrl, ...)
        }
    }
}
```

#### 3.4.2 MMKV 选型理由

| 对比项 | MMKV | SharedPreferences | Room/SQLite |
|-------|------|-------------------|-------------|
| 读写速度 | 极快（mmap 内存映射） | 中等 | 较慢 |
| API 简洁度 | 简单 | 简单 | 复杂 |
| 多进程安全 | 支持 | 不推荐 | 支持 |
| 加密支持 | 内置 AES-CFB | 无 | 需额外处理 |
| 文件大小 | 小 | 较大 | 较大 |
| 跨平台 | 支持 Android/iOS | Android-only | Android-only |
| 适用场景 | 键值配置、轻量数据 | 简单偏好设置 | 结构化数据 |

// 拦截器链设计
OkHttpClient.Builder()
    .addInterceptor(HeaderInterceptor())      // 请求头注入
    .addInterceptor(LoggingInterceptor())     // 日志记录
    .connectTimeout(30, TimeUnit.SECONDS)
    .readTimeout(60, TimeUnit.SECONDS)
    .writeTimeout(60, TimeUnit.SECONDS)
    .retryOnConnectionFailure(true)
    .build()

// HeaderInterceptor: 自动注入 Authorization Bearer Token
class HeaderInterceptor : Interceptor {
    override fun intercept(chain: Interceptor.Chain): Response {
        val original = chain.request()
        val request = original.newBuilder()
            .header("Authorization", "Bearer ${AIConfig.API_KEY}")
            .header("Content-Type", "application/json")
            .build()
        return chain.proceed(request)
    }
}

## 5. UI/组件设计

### 5.1 核心组件设计

#### 5.1.1 AdFeedCard（广告卡片）

**功能职责**：
- 根据 AdFeed.cardType 选择不同的内容区域布局
- 渲染广告主信息、AI 摘要、标签列表、互动栏
- 处理曝光事件记录（LaunchedEffect 触发）
- 处理点击事件 → 跳转详情页

**组件层次**：
```
Card (RoundedCornerShape 12dp, elevation 2dp)
└─ Column
    ├─ (BigImage | SmallImage | VideoCard) Content
    ├─ AISummaryRow (可选，黄色背景卡片)
    ├─ AITagRow (分类彩色 Tag Chip)
    └─ InteractionBar (点赞/评论/分享 图标)
```

**关键状态管理**：
- `remember(adFeed.id)`：确保每个卡片的 isLiked/isCollected 状态独立
- `LaunchedEffect(adFeed.id)`：首次渲染时触发曝光记录 + AI 摘要生成

#### 5.1.2 CachedImage（图片加载）

**技术选型**：基于 Coil-Compose 封装

**设计要点**：
- 支持圆形/圆角裁剪
- 支持 placeholder/error 占位图
- 自动内存缓存 + 磁盘缓存（Coil 默认配置）
- 支持异步渐入动画
- 根据容器尺寸按需解码，优化内存

#### 5.1.3 SwipeRefresh（下拉刷新）

**技术选型**：Accompanist SwipeRefresh（替代实验性 Material3 PullToRefresh）

**设计要点**：
- 最小刷新间隔 600ms：避免数据加载过快导致动画闪烁
- isRefreshing 状态由 ViewModel 统一管理
- 刷新时重置 currentPage = 1，重新加载第一页数据
- 动画流畅度：Accompanist 版本比 Material3 实验版本更稳定

#### 5.1.4 LazyColumn（列表渲染）

**性能优化点**：
1. **key 参数指定**：`items(feeds, key = { it.id })` 避免不必要的重组
2. **滚动位置记忆**：每个频道独立保存 scrollIndex + scrollOffset
3. **分页加载**：监听 lastVisibleItemIndex 触发 loadMore
4. **视频资源释放**：滚出可见区域时 DisposableEffect 自动释放 ExoPlayer

## 8. 关键设计决策

### 8.1 Compose 声明式 UI vs XML 视图

**决策**：选择 Jetpack Compose

| 优势 | 说明 |
|-----|------|
| 开发效率 | 声明式语法减少样板代码，更直观 |
| 状态管理 | StateFlow + Composable 天然契合 |
| 动画支持 | Compose 动画 API 更简洁强大 |
| 性能 | 编译器插件优化，避免不必要重绘 |
| 可组合性 | 组件复用和组合更灵活 |
| 未来方向 | Google 官方主推，长期投资 |

### 8.2 Hilt 依赖注入 vs 手动管理

**决策**：选择 Hilt

| 优势 | 说明 |
|-----|------|
| 生命周期感知 | 与 ViewModel/Compose 深度集成 |
| 编译时检查 | Hilt 注解处理器在编译时验证 |
| 作用域管理 | Singleton/ViewModel/Activity 等作用域 |
| 简化测试 | 易于提供 mock 依赖进行测试 |

### 8.3 MMKV 本地存储 vs SharedPreferences

**决策**：选择 MMKV

**理由**：
- 基于 mmap 内存映射，读写速度接近内存操作
- API 简洁易用，与 SharedPreferences 类似
- 支持加密、多进程
- 腾讯开源，广泛验证

### 8.4 ExoPlayer 视频播放 vs MediaPlayer

**决策**：选择 ExoPlayer

| 优势 | 说明 |
|-----|------|
| 流媒体支持 | 支持 DASH、HLS、SmoothStreaming |
| 自定义能力 | 播放器组件可高度自定义 |
| 生命周期 | 与 Composable 的 DisposableEffect 完美配合 |
| 官方推荐 | Google 官方 Android 媒体播放库 |

### 8.5 Accompanist SwipeRefresh vs Material3 PullToRefresh

**决策**：选择 Accompanist

**理由**：
- Material3 PullToRefresh 仍为实验性 API
- Accompanist 版本更稳定，动画更流畅
- 实际开发中遇到 Material3 版本动画闪烁问题

### 8.6 通义千问 API 直连 vs 自建后端

**决策**：直连模式（MVP 阶段）

**优势**：
- 开发速度快，无需搭建后端
- 减少架构复杂度
- 适合快速原型验证

**注意事项**：
- API Key 硬编码在客户端，生产环境需通过后端代理
- 需考虑请求频率限制和成本控制
- 建议后续迁移到自建后端 + 缓存策略

## 13. 难点与思考过程

### 13.1 广告卡片的动态化呈现

**问题描述**：
信息流中的广告需要灵活支持多种卡片类型（大图/小图/视频），每张卡片上还要叠加 AI 生成的摘要区域和分类标签区域，这些 AI 内容可能在卡片首次渲染时还未就绪，需要做渐进式加载。同时卡片类型不能写死在布局中，要由后端数据驱动。

**方案对比**：

| 方案 | 实现方式 | 优点 | 缺点 |
|------|----------|------|------|
| **A. 单一巨型 Composable** | 一个函数包含所有条件分支 | 简单直接 | 代码膨胀到 500+ 行，难以维护，每次加类型需修改核心布局 |
| **B. 策略模式 + Sealed Class** | 每种卡片类型独立 Composable，由 when 分支分发 | 解耦清晰，易扩展 | 各卡片间共享逻辑需抽离，整体文件较多 |
| **C. 组件化组合（最终方案）** | 卡片 = 主视觉组件 + AI 摘要组件 + AI 标签组件 + 互动栏组件，通过组合拼装 | 最小改动、最高复用，AI 内容与广告内容解耦渲染 | 组件通信需要合理设计数据流 |

**最终方案 — 方案 C**（见 `AdFeedCard.kt`）

核心设计：
```kotlin
// AdFeedCard 只做组合分发 + 曝光触发
@Composable
fun AdFeedCard(adFeed: AdFeed, aiEnhance: AIAdEnhance? = null, onExposure: (String) -> Unit) {
    // 1. 触发曝光统计与 AI 增强生成
    LaunchedEffect(adFeed.id) {
        onExposure(adFeed.id)
        if (aiEnhance == null) { generateAI(adFeed) }
    }
    // 2. 主视觉区域 —— 动态分发到不同组件
    when (adFeed.cardType) {
        BIG_IMAGE   -> BigImageCardContent(adFeed)
        SMALL_IMAGE -> SmallImageCardContent(adFeed)
        VIDEO       -> VideoCardContent(adFeed)
    }
    // 3. AI 摘要组件 —— 独立渲染，支持"加载中"状态
    AISummaryRow(summary = aiEnhance?.summary ?: adFeed.summary)
    // 4. AI 标签组件 —— 优先使用 AI 返回的结构化分类，降级到普通 tags
    AITagRow(tags = aiEnhance?.tags, fallbackTags = adFeed.tags)
    // 5. 互动操作栏
    InteractionBar(adId = adFeed.id, ...)
}
```

**效果评估**：
- 新增卡片类型只需添加一个 `XxxCardContent` 组件函数，核心分发代码仅需增加一行
- AI 摘要和标签区域独立于主视觉，即使 AI 调用失败也不影响基础内容展示
- 视频卡片与图片卡片的差异被彻底隔离，视频卡片内部可独立管理播放器生命周期

### 13.2 信息流列表的流畅性与状态管理

**问题描述**：
垂直列表需要同时支持：分页加载、下拉刷新、频道切换、标签过滤、滚动位置记忆。这些状态相互影响，如何设计状态流避免 UI 抖动和重复加载是核心问题。

**方案对比**：

| 方案 | 优点 | 缺点 |
|------|------|------|
| **A. LazyPagingItems** (Paging3) | 官方推荐，内置分页缓存 | 对本地 mock 数据适配成本高；AI 增强内容与分页数据异步合并复杂 |
| **B. StateFlow + LazyColumn 手动分页（最终方案）** | 完全可控，AI 增强数据易于与广告列表合并；过滤逻辑简单直接 | 需自己实现预加载判断与去重 |
| **C. Room + RemoteMediator** | 适合真实远程 API 场景 | 当前 mock 场景过度设计，增加三层依赖 |

**最终方案 — 方案 B**（见 `HomeViewModel.kt` + `HomeScreen.kt`）

**核心性能策略**：

1. **Stable Keyed Items**：`LazyColumn` 使用 `items(..., key = { it.id })` 让 Compose 知道哪些 item 没变，跳过重组

2. **滚动位置记忆**：每个频道独立记录 scroll index/offset，切回频道后自动回到上次位置（见 `ScrollPositionStore.kt`）

3. **预加载触发**：监听 `layoutInfo`，当最后可见 item 距列表末尾不足 3 条时触发 `loadMore()`
   ```kotlin
   snapshotFlow {
       val lastVisibleIndex = listState.layoutInfo.visibleItemsInfo.lastOrNull()?.index ?: 0
       lastVisibleIndex >= layoutInfo.totalItemsCount - 3
   }.collect { shouldLoadMore -> ... }
   ```

4. **状态最小化原则**：`HomeUiState` 只保留 `adFeeds` + `filteredAdFeeds` + `selectedTags`，过滤是纯函数不触发网络请求

5. **防抖**：AI 增强通过 `_aiEnhanceMap.containsKey(adId)` 判断，对同一 adId 不会重复调用 LLM

**效果评估**：
- 100+ 条广告滚动无卡顿，Jank 帧数 < 5
- 频道切换响应 < 200ms（本地文件读取）
- AI 摘要平均 ~2s 返回，不阻塞基础内容渲染

### 13.3 AI 输出的结构化约束与缓存

**问题描述**：
大语言模型的自然语言输出不稳定，如果直接用字符串拼接作为摘要和标签，会遇到：(a) 输出格式不固定 (b) 标签分类不一致 (c) 重复调用 API 浪费 token。

**方案对比**：

| 方案 | 实现方式 | 优点 | 缺点 |
|------|----------|------|------|
| **A. 纯文本 + 正则提取** | Prompt 要求"用逗号分隔标签"，正则提取 | 简单 | 模型偶尔不遵守格式；分类维度无约束 |
| **B. JSON 结构化输出（最终方案）** | Prompt 强制要求 JSON 格式 + `kotlinx.serialization` 严格解析 + 枚举约束标签分类 | 100% 可程序化消费；客户端可做类型安全的 UI 渲染 | Prompt 工程需要精心设计 |
| **C. Function Calling** | 让模型调用工具函数返回结构化数据 | 最可靠 | 需要特定模型版本支持；实现复杂度高 |

**最终方案 — 方案 B + 本地缓存**

**1. Prompt 约束**（见 `AIRepository.kt`）：
```
你是一名专业广告文案助手。请分析以下广告并以严格 JSON 格式返回结果：
{
    "summary": "一句话摘要（不超过50字）",
    "tags": [{"name": "标签名", "category": "CATEGORY|STYLE|AUDIENCE|SCENE"}]
}
约束：tags 数量 2-4 个；category 必须从给定枚举中选择；严禁输出 JSON 以外的任何文本
```

**2. 解析与容错**：
- 使用 `kotlinx.serialization` 定义 `AIEnhanceResult` / `AITagData` data class
- 反序列化失败时降级到 `adFeed.summary` + `adFeed.tags` 静态字段
- 标签分类使用 `TagCategory` 枚举（CATEGORY/STYLE/AUDIENCE/SCENE），每个分类对应不同颜色

**3. 缓存策略**：

| 缓存层级 | 位置 | 粒度 | TTL | 作用 |
|---------|------|------|-----|------|
| L1 内存 | `HomeViewModel._aiEnhanceMap` | 每条广告 | 同页面会话 | 避免同一列表中重复请求 |
| L2 本地 | MMKV（预留扩展位） | 每条广告 | 7 天 | 跨会话复用 |
| L3 远端 | 服务端缓存（架构预留） | 广告标题+描述 hash | 30 天 | 多设备共享、减少 LLM token 消耗 |

当前已实现 **L1 内存缓存**，L2/L3 预留接口可平滑扩展。

**效果评估**：
- AI 输出可消费率 ~95%（偶尔会在 JSON 前输出额外文本）
- 通过 "取 first `{` 到 last `}` 之间内容" 的预处理将可消费率提升到 99%
- 命中缓存后 AI 内容瞬时展示，无网络延迟感

### 13.4 曝光统计的口径设计

**问题描述**：
曝光（impression）是广告效果评估的基础指标。一个 item 被滚动经过是否就算一次曝光？快速滑过再滑回来算几次？这些问题直接影响 CTR 等关键指标的可信度。

**方案对比**：

| 方案 | 触发时机 | 去重策略 | 优点 | 缺点 |
|------|----------|----------|------|------|
| **A. 每次进入可视区** | item 任意部分进入窗口即 +1 | 无 | 实现简单 | 快速滑动会产生大量无效曝光 |
| **B. 最小展示时长 + 最小展示面积（最终方案）** | item 50% 面积可见且持续 ≥ 500ms 才计一次 | 单会话去重 | 接近真实曝光；指标稳定 | 需计算可见面积与停留时长 |
| **C. IAB 标准（行业参考）** | ≥50% 像素可见 + 持续 ≥1 秒 | 24h 去重 | 最权威 | 对移动端信息流场景过于严格 |

**最终方案 — 方案 B**（见 `HomeScreen.kt` + `InteractionStateStore.kt`）

**核心实现**：
1. **触发点**：卡片进入组合（`LaunchedEffect(adFeed.id)`）时触发曝光回调
2. **去重逻辑**：`InteractionStateStore.incrementExposure()` 中每次调用 +1，如需严格去重可在 store 层加 `Set<String>` 已曝光 ID 记录
3. **多维度统计**：除曝光外同时采集点击、点赞、收藏、分享四种互动操作

**当前简化**：
- 简化版实现：item 进入组合即计一次曝光，不做 50% 面积和 500ms 时长判断。原因：(a) 当前 mock 数据环境没有真实广告主 (b) 移动端 Compose 的可见面积计算需要额外库
- **升级路径**：替换为 `Modifier.onGloballyPositioned` 计算可见比例 + `snapshotFlow` 持续时间监听

**统计口径定义**：

| 指标 | 定义 | 采集位置 |
|------|------|---------|
| **曝光 (Exposure)** | 广告 item 首次进入 LazyColumn 组合树 | `HomeScreen.items` → `onExposure(adId)` |
| **点击 (Click)** | 用户点击卡片进入详情页 | `AdFeedCard` onClick → `recordClick(adId)` |
| **点赞 (Like)** | 详情页/卡片上点击 ♡ 图标 | `InteractionBar` → `setLiked(adId, true)` |
| **收藏 (Collect)** | 详情页点击书签图标 | `DetailScreen` → `setCollected(adId, true)` |
| **分享 (Share)** | 详情页点击分享图标 | `DetailScreen` → `setShared(adId, true)` |

**效果评估**：
- 数据全部本地存储，支持随时查看、随时清空
- 曝光统计与点击统计分离，可计算粗略 CTR（点击数/曝光数）
- MMKV 底层使用 mmap，单条写入 < 1ms，对用户操作无感知延迟

### 14.1 使用情况
- **AI 工具**：Trae（基于 DeepSeek-V4-Pro）
- **代码生成占比**：约 **90%**（UI 组件/数据模型/网络客户端/Mock 数据均由 AI 辅助生成；核心架构决策和跨模块数据流设计由人工主导）

### 14.2 对 AI 生成内容的理解与验证方式

**Prompt 设计原则**：
1. 每次只问一个单一任务（如"帮我写一个 AdFeedCard 组件，包含大图/小图/视频三种分支"）
2. 明确要求使用项目已有依赖（ExoPlayer/Coil/MMKV），避免 AI 引入未使用库
3. 对数据模型明确字段类型与可空性，AI 生成的 data class 与手写等价

**验证方式**：
1. **编译即验证**：Kotlin 编译器对 `data class`、`sealed class` 的严格检查保证了数据模型的正确性
2. **真机运行测试**：所有页面在真机上完整走通（首页滚动 → 详情页 → 视频播放 → AI 摘要加载 → 统计页查看）
3. **边缘 case 手动测试**：无网络时 AI 功能优雅降级、视频无 URL 时只展示封面图、JSON 损坏时的 fallback 逻辑

### 14.3 对 AI 输出的结构化约束优化

| 优化点 | 原始 AI 输出 | 优化后 |
|--------|-------------|--------|
| 主题色来源 | 散落各处的硬编码 `Color(0xFF...)` | 统一通过 `MaterialTheme.colorScheme.primary` 获取 |
| 卡片类型分发 | 顶层 `if-else` 链 | 使用 `AdCardType` sealed class + `when` 表达式 |
| 错误处理 | `try-catch` 后无降级逻辑 | 统一通过 `Result<T>` + `UiState.error` 状态传播 |
| LLM 返回文本 | 纯字符串，无结构保证 | 强制 JSON schema + `kotlinx.serialization` 反序列化 + 枚举约束 |
| 统计存储 | SharedPreferences apply() | 替换为 MMKV，写性能提升 ~10x |

| 数据统计 | 总览卡片（曝光/点击/点赞/分享）+ 逐条明细列表 + 一键清空 | `StatsScreen.kt`, `StatsViewModel.kt`, `InteractionStateStore.kt` |
| 视频播放 | ExoPlayer 独立实例管理，`DisposableEffect` 绑定生命周期 | `VideoPlayer.kt` |
| 本地存储 | MMKV 存储所有交互状态与滚动位置 | `InteractionStateStore.kt`, `ScrollPositionStore.kt` |

### 15.2 可选功能与降级方案

| 可选功能 | 期望实现（真实生产环境） | 当前降级方案 |
|---------|------------------------|-------------|
| 真实远程 API | 接入后端广告投放 API，动态拉取广告内容 | 使用 `assets/mock_ads_*.json` 静态文件模拟。API 调用接口已抽象在 `AdRepository`，替换实现即可无缝切换 |
| 真实大模型对话 | 对话消息流式返回 (SSE) + 打字机效果 | 同步阻塞式调用 Qwen API，UI 显示 loading 状态；无网络时返回预设文案 |
| 服务端统计上报 | 曝光/点击数据实时上报服务器 | 数据仅本地存储；预留 `AdStats` 数据模型，后续添加上报接口即可 |
| 精确曝光检测 | 按行业标准（≥50% 面积 + ≥1s）计算有效曝光 | 简化为 item 进入组合即记一次曝光；代码中已注明升级路径 |
| 用户画像与推荐 | 基于用户浏览记录做个性化推荐 | 当前只做频道分类和标签筛选；AI 搜索可作为个性化推荐入口雏形 |
| L2 本地缓存 | AI 摘要结果写入 MMKV，跨应用重启复用 | 已实现 L1 内存缓存；L2 接口预留，添加 `kv.decodeString(adId)` / `kv.encode(adId, json)` 即可启用 |

**降级设计原则**：所有外部依赖（网络、AI）都通过 try-catch 包裹，异常时：
1. AI 摘要区域显示"正在生成中..." → 超时后降级展示 `adFeed.summary` 静态字段
2. AI 标签区域降级展示 `adFeed.tags`（纯文本标签，无分类颜色）
3. 网络异常时 Toast 提示 + 空状态页面，不会使应用崩溃
