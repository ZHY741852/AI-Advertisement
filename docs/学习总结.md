# AI-Advertisement 项目学习总结

## 1. 项目概述与收获

这是一个使用 **Jetpack Compose + MVVM + Clean Architecture** 开发的现代 Android 应用，在开发过程中遇到了多个典型问题，积累了丰富的实战经验。

### 1.1 项目特点总结

| 技术领域 | 关键经验 |
|---------|---------|
| **Jetpack Compose** | 声明式 UI 的思维转变、状态管理、副作用 API、LazyColumn 性能优化 |
| **依赖注入 (Hilt)** | ViewModel 注入、Composable 层的 hiltViewModel() 使用、作用域管理 |

| **视频播放** | ExoPlayer 在 Compose 中的生命周期管理、资源释放、实例复用问题 |
| **本地存储** | MMKV 的轻量级存储能力、滚动位置持久化、用户交互记录 |
| **网络架构** | Retrofit + OkHttp 拦截器链、suspend 函数协程化请求、序列化配置 |

## 2. 棘手问题与解决方案

### 2.1 问题一：所有视频卡片播放同一个视频

#### 2.1.1 现象描述
- 所有视频卡片显示相同的视频内容
- 切换频道后，新的卡片仍播放之前的视频
- 即使 videoUrl 在 JSON 中已正确配置为不同 URL，播放器仍播放旧视频

#### 2.1.2 问题分析

**根本原因 1：ExoPlayer 实例复用导致状态错乱**

```kotlin
// ❌ 错误实现（原始代码）
@Composable
fun ThumbnailVideoPlayer(videoUrl: String, ...) {
    var player: ExoPlayer? by remember { mutableStateOf(null) }
    // ↑ 没有使用 videoUrl 作为 remember 的 key！
    // 当 LazyColumn 回收/复用时，这个 player 状态没有与特定 URL 绑定
    // 多个卡片实际上共享/复用了同一个 ExoPlayer 实例

    DisposableEffect(Unit) {  // ❌ key = Unit，永远不会重新触发
        // 这个 effect 只会执行一次，URL 变化时不会重建播放器
        val exoPlayer = ExoPlayer.Builder(context).build().apply {
            setMediaItem(MediaItem.fromUri(videoUrl))
            prepare()
            playWhenReady = autoPlay
        }
        player = exoPlayer
        onDispose { exoPlayer.release() }
    }

    AndroidView(...) { playerView ->
        playerView.player = player
    }
}
```

**根本原因 2：VideoCardContent 播放状态也没有正确 key**

```kotlin
// ❌ 错误实现（原始代码）
@Composable
private fun VideoCardContent(adFeed: AdFeed) {
    var isPlaying by remember { mutableStateOf(false) }
    // ↑ 没有 key，所有卡片的 isPlaying 状态互相干扰！
    // 点击卡片 A 的播放按钮，卡片 B 也会进入播放状态

    Box {
        if (!isPlaying) {
            CachedImage(...)  // 显示缩略图 + 播放按钮
        } else {
            ThumbnailVideoPlayer(videoUrl = adFeed.videoUrl ?: "", ...)
            // ↑ 但进入此分支后，VideoPlayer 的 remember 又会出问题
        }
    }
}
```

**根本原因 3：JSON 数据中部分 videoUrl 为空**

```json
// ❌ 原始 mock_ads_travel.json 片段
{
    "id": "tr_002",
    "cardType": "video",  // ← 声明为视频卡片
    "videoUrl": null,     // ← 但 videoUrl 为空！
    "thumbnailUrl": null
}
// ExoPlayer 收到 null/空 URL 后会播放缓存内容或报错
```

**根本原因 4：Picsum 图片 URL 格式错误**

```
// ❌ 旧格式（每次请求返回随机图片）
https://picsum.photos/800/600?random=xxx

// ✅ 正确格式（seed 参数确保同一 ID 返回相同图片）
https://picsum.photos/seed/xxx/800/600
```

#### 2.1.3 解决方案

**修复方案 1：VideoPlayer 中使用 URL 作为 remember key**

```kotlin
// ✅ 正确实现
@Composable
fun ThumbnailVideoPlayer(videoUrl: String, ...) {
    val context = LocalContext.current
    var player: ExoPlayer? by remember(videoUrl) { mutableStateOf(null) }
    // ↑ key = videoUrl：每个 URL 有独立的播放器状态

    val hasValidUrl = videoUrl.isNotBlank()
        && android.net.Uri.parse(videoUrl).scheme != null
    // ↑ 增加 URL 合法性检查

    if (hasValidUrl) {
        DisposableEffect(videoUrl) {  // ✅ key = videoUrl，URL 变化重建播放器
            val exoPlayer = ExoPlayer.Builder(context).build().apply {
                setMediaItem(MediaItem.fromUri(videoUrl))
                prepare()
                playWhenReady = autoPlay
            }
            player = exoPlayer
            onDispose {
                exoPlayer.release()
                player = null
            }
        }
        AndroidView(...) { playerView ->
            playerView.player = player
        }
    } else {
        // ✅ URL 无效时降级显示缩略图
        if (thumbnailUrl != null) {
            CachedImage(imageUrl = thumbnailUrl, ...)
        }
    }
}
```

**修复方案 2：VideoCardContent 使用 adFeed.id 作为 key**

```kotlin
// ✅ 正确实现
@Composable
private fun VideoCardContent(adFeed: AdFeed) {
    var isPlaying by remember(adFeed.id) { mutableStateOf(false) }
    // ↑ key = adFeed.id：每个卡片有独立的播放状态

    val hasValidVideo = !adFeed.videoUrl.isNullOrBlank()
        && android.net.Uri.parse(adFeed.videoUrl).scheme != null

    Box {
        if (!isPlaying || !hasValidVideo) {
            // 显示缩略图
            CachedImage(imageUrl = adFeed.thumbnailUrl, ...)
            // 只有有效视频才显示播放按钮
            if (hasValidVideo) {
                Box(Modifier.align(Alignment.Center)
                    .size(64.dp)
                    .clip(CircleShape)
                    .background(Color.Black.copy(alpha = 0.6f))
                    .clickable { isPlaying = true }
                ) { Icon(...) }
            }
        } else {
            // 点击播放后才初始化播放器
            ThumbnailVideoPlayer(
                videoUrl = adFeed.videoUrl ?: "",
                thumbnailUrl = adFeed.thumbnailUrl,
                ...
            )
        }
    }
}
```

**修复方案 3：修复 JSON mock 数据**

- 为所有 `cardType = "video"` 的条目填写有效的 `videoUrl`
- 将 `https://picsum.photos/800/600?random=xxx` 改为 `https://picsum.photos/seed/xxx/800/600`

#### 2.1.4 经验总结

| 学习点 | 具体内容 |
|-------|---------|
| **Compose remember key** | 状态如果与某个 ID 相关，必须把该 ID 作为 remember 的 key。否则 LazyColumn 复用组件时，状态会错乱。 |
| **DisposableEffect key** | `DisposableEffect(key)` 的 key 决定何时重新执行副作用。如果依赖外部参数（如 URL），必须将其作为 key。 |
| **Composable 可复用性** | 视频播放器这类带有外部资源的 Composable，必须确保参数变化时能正确重建，否则会出现"旧资源复用"问题。 |
| **防御式编程** | 永远不要假设数据是完美的。JSON 可能有 null/空字符串、URL 可能无效、网络可能失败。增加 `hasValidUrl` 检查 + fallback 方案。 |
| **LazyColumn 回收机制** | LazyColumn 会回收离屏的 Composable，但 remember 的状态可能被错误复用。key 参数对于列表项的状态管理至关重要。 |
| **ExoPlayer 生命周期** | 必须在 onDispose 中调用 release()。如果多个组件共用一个播放器实例（错误做法），release 时机就会非常危险。 |

### 2.2 问题二：下拉刷新动画不流畅，刷新图标滞留

#### 2.2.1 现象描述
- 使用 Material3 的 `PullToRefreshBox` 时，下拉释放后刷新图标不消失
- 动画有明显卡顿感，体验差
- 有时图标会卡在屏幕上需要手动滚动才消失

#### 2.2.2 问题分析

**根本原因 1：Material3 PullToRefreshBox 仍为实验性 API**

```kotlin
// @OptIn(ExperimentalMaterial3Api::class)
// PullToRefreshBox 是 experimental，存在以下问题：
// - 在某些设备上动画不流畅
// - isRefreshing 状态变化时图标消失延迟
// - 与 LazyColumn 的滚动交互有 bug
```

**根本原因 2：数据加载太快，动画来不及播放**

```kotlin
// ❌ 原始实现
fun refresh() {
    viewModelScope.launch {
        _uiState.value = _uiState.value.copy(isRefreshing = true)
        val items = mockDataProvider.getAdFeeds(...)  // ← 本地读取，50ms 完成
        _uiState.value = _uiState.value.copy(
            isRefreshing = false,  // ← 立即置为 false，动画刚启动就结束
            adFeeds = items.items
        )
    }
}
// 动画需要至少 500-600ms 才能平滑播放
// 但数据加载 50ms 完成，动画"秒闪"一下就结束，视觉上很突兀
```

#### 2.2.3 解决方案

**修复方案 1：替换为 Accompanist SwipeRefresh**

```kotlin
// ✅ 正确实现（HomeScreen.kt）
import com.google.accompanist.swiperefresh.SwipeRefresh
import com.google.accompanist.swiperefresh.rememberSwipeRefreshState

@OptIn(ExperimentalMaterial3Api::class)
@Composable
fun HomeScreen(...) {
    Scaffold(...) { paddingValues ->
        val swipeRefreshState = rememberSwipeRefreshState(
            isRefreshing = uiState.isRefreshing
        )
        SwipeRefresh(
            state = swipeRefreshState,
            onRefresh = { viewModel.refresh() },
            modifier = Modifier
                .fillMaxSize()
                .padding(paddingValues)
        ) {
            // 列表内容
        }
    }
}
```

**修复方案 2：增加最小刷新间隔**

```kotlin
// ✅ 正确实现（HomeViewModel.kt）
fun refresh() {
    currentPage = 1
    val channel = _uiState.value.currentChannel
    viewModelScope.launch {
        _uiState.value = _uiState.value.copy(isRefreshing = true, error = null)

        val startTime = System.currentTimeMillis()
        val minRefreshDuration = 600L  // ← 最小刷新时间 600ms

        try {
            val items = mockDataProvider.getAdFeeds(channel.key, 1, pageSize)
            val allTags = collectAllTags(items.items)

            // 如果加载太快，等待一段时间，让用户看到动画
            val elapsed = System.currentTimeMillis() - startTime
            if (elapsed < minRefreshDuration) {
                kotlinx.coroutines.delay(minRefreshDuration - elapsed)
            }

            _uiState.value = _uiState.value.copy(
                adFeeds = items.items,
                filteredAdFeeds = applyTagFilter(items.items, _uiState.value.selectedTags),
                allAvailableTags = allTags,
                isRefreshing = false,
                hasMore = items.hasMore
            )
        } catch (e: Exception) {
            // 失败也要等待，避免动画闪烁
            val elapsed = System.currentTimeMillis() - startTime
            if (elapsed < minRefreshDuration) {
                kotlinx.coroutines.delay(minRefreshDuration - elapsed)
            }
            _uiState.value = _uiState.value.copy(isRefreshing = false, error = e.message)
        }
    }
}
```

#### 2.2.4 经验总结

| 学习点 | 具体内容 |
|-------|---------|
| **实验性 API 风险** | 带有 `@Experimental...Api` 注解的 API 可能存在稳定性问题。生产环境需评估风险，有时选择成熟稳定库更好。 |
| **动画与数据的协同** | UI 动画有自身的时间轴，不能完全被数据加载速度驱动。需要人工注入"最小间隔"，保证视觉体验。 |
| **库选型权衡** | Material3 是官方推荐方向，但 Accompanist 更稳定。选择时要平衡"未来兼容性"与"当前稳定性"。 |
| **错误处理也要考虑 UX** | 加载失败时同样需要考虑动画体验，不能让用户看到"一闪就消失"的奇怪动画。 |

### 2.3 问题三：Compose 编译错误 - DisposableEffect 提前 return

#### 2.3.1 现象描述

```kotlin
@Composable
fun ThumbnailVideoPlayer(videoUrl: String, ...) {
    val hasValidUrl = videoUrl.isNotBlank() && ...

    DisposableEffect(videoUrl, hasValidUrl) {
        if (!hasValidUrl) {
            onDispose { }
            return@DisposableEffect  // ❌ 编译错误！
        }
        // 创建播放器...
        onDispose { exoPlayer.release() }
    }
}
```

编译报错：
```
e: file:///.../VideoPlayer.kt:92:13 This function must return a value of type DisposableEffectResult
e: file:///.../VideoPlayer.kt:92:13 Type mismatch: inferred type is Unit but DisposableEffectResult was expected
```

#### 2.3.2 问题分析

`DisposableEffect` 的 lambda 必须在末尾返回 `DisposableEffectResult`，这个结果是通过调用 `onDispose { ... }` 产生的。提前 return 会导致返回类型为 `Unit` 而非 `DisposableEffectResult`。

Compose 的副作用 API 设计约束：
- `LaunchedEffect`：返回 `Unit`，可以提前 return
- `DisposableEffect`：必须返回 `DisposableEffectResult`，**不能提前 return**
- `SideEffect`：返回 `Unit`

#### 2.3.3 解决方案

**方案：将检查逻辑移到 DisposableEffect 外部，使用 if-else**

```kotlin
// ✅ 正确实现
@Composable
fun ThumbnailVideoPlayer(videoUrl: String, ...) {
    val hasValidUrl = videoUrl.isNotBlank() && ...

    if (hasValidUrl) {
        // 在合法分支内创建 DisposableEffect
        DisposableEffect(videoUrl) {  // ← 简化 key，只依赖 URL
            val exoPlayer = ExoPlayer.Builder(context).build().apply {
                setMediaItem(MediaItem.fromUri(videoUrl))
                prepare()
                playWhenReady = autoPlay
            }
            player = exoPlayer
            onDispose {
                exoPlayer.release()
                player = null
            }
        }
        AndroidView(...) { playerView ->
            playerView.player = player
        }
    } else {
        // URL 无效时的降级 UI
        if (thumbnailUrl != null) {
            CachedImage(...)
        }
    }
}
```

#### 2.3.4 经验总结

| 学习点 | 具体内容 |
|-------|---------|
| **Compose 副作用 API 限制** | `DisposableEffect` 的 lambda 必须最后一行是 `onDispose { ... }`，不能有提前 return 的分支。 |
| **思维方式转变** | 在 Compose 中，优先使用"声明式分支（if/else）"而非"命令式提前返回"。if-else 让分支各自处理自己的逻辑，更清晰。 |
| **资源创建的条件性** | 不要在 DisposableEffect 内部做条件判断。把判断提到 Composable 层面，让每个分支独立决定是否创建副作用。 |
| **Kotlin Lambda 返回值** | Compose 的很多 API 依赖 lambda 最后一行表达式作为返回值。提前 return 会破坏这一设计。 |

## 3. 踩坑复盘

### 3.1 坑一：JSON 中文字符编码问题

**现象**：
```
ConvertFrom-Json : Invalid JSON primitive: xxx
// 或
kotlinx.serialization.json.internal.JsonDecodingException:
  Unexpected JSON token at offset...
```

**原因**：
- JSON 文件未使用 UTF-8 (无 BOM) 格式保存
- Windows PowerShell 默认使用 GBK/CP936 编码，写入 JSON 时破坏 UTF-8 文件
- JSON 字符串中包含未转义的控制字符

**解决方案**：
1. 使用 IDE 编辑 JSON，确认编码为 UTF-8
2. 使用 `System.IO.File.WriteAllText(path, content, UTF8Encoding(false))` 写入文件
3. 在 JSON 解析配置中设置 `isLenient = true` 增强容错性

```kotlin
val json = Json {
    ignoreUnknownKeys = true   // 忽略未知字段
    coerceInputValues = true    // 类型不匹配时使用默认值
    encodeDefaults = true
    isLenient = true            // ← 宽松模式，容忍部分格式问题
}
```

### 3.2 坑二：remember(key) vs remember 的区别

**易错点总结**：

| 写法 | 行为 | 适用场景 |
|-----|------|---------|
| `remember { ... }` | 仅首次初始化，永远不更新 | 常量、固定配置 |
| `remember(key1, key2) { ... }` | key 变化时重新计算 | 依赖外部参数的状态 |
| `rememberSaveable { ... }` | 配置变更（如旋转屏幕）后恢复 | 用户输入、滚动位置 |

**常见误用**：
```kotlin
// ❌ 错误：videoUrl 变化时，player 仍然是旧值
var player by remember { mutableStateOf<ExoPlayer?>(null) }

// ✅ 正确：URL 变化时重新初始化播放器
var player by remember(videoUrl) { mutableStateOf<ExoPlayer?>(null) }

// ❌ 错误：每个卡片的 isPlaying 状态互相干扰
var isPlaying by remember { mutableStateOf(false) }

// ✅ 正确：每个卡片 ID 有独立状态
var isPlaying by remember(adFeed.id) { mutableStateOf(false) }
```

### 3.3 坑三：Hilt + Compose ViewModel 注入细节

**现象**：

### 3.4 坑四：Compose 中 AndroidView 的状态同步

**现象**：
- ExoPlayer 的播放状态与 Compose 的 `isPlaying` 状态不同步
- 卡片回收后再次出现时，`AndroidView` 显示异常

**原因**：
- `AndroidView` 是原生 View，其内部状态与 Compose 状态是两套系统
- 需要在 `update` lambda 中显式同步 Compose state → View 属性

**最佳实践**：
```kotlin
AndroidView(
    factory = { ctx ->
        PlayerView(ctx).apply {
            // 仅初始化时执行，设置一次性属性
            this.useController = true
            layoutParams = ViewGroup.LayoutParams(
                ViewGroup.LayoutParams.MATCH_PARENT,
                ViewGroup.LayoutParams.MATCH_PARENT
            )
        }
    },
    update = { playerView ->
        // ← Compose state 变化时执行，同步到 View
        playerView.player = player
        // 如需要监听播放器事件，在这里设置 listener
    }
)
```

### 3.5 坑五：通义千问 API 的 JSON 解析

**现象**：
- AI 返回的文本常常被包裹在 ````json ... ``` ` 代码块中
- JSON 中常有换行、缩进等格式字符
- 偶尔返回的不是 JSON 而是纯文本解释

**解决方案**：
```kotlin
private fun parseEnhanceResult(content: String): AIAdEnhance {
    // 1. 去除代码块包裹标记
    val cleanContent = content
        .trim()
        .removePrefix("```json")
        .removePrefix("```JSON")
        .removePrefix("```")
        .removeSuffix("```")
        .trim()

    return try {
        // 2. 使用宽松配置解析
        val result = jsonParser.decodeFromString<AIEnhanceResult>(cleanContent)
        // 3. 映射到业务模型（处理 category 枚举转换）
        val tagList = result.tags.mapNotNull { tagData ->
            val category = when (tagData.category.uppercase()) {
                "CATEGORY" -> TagCategory.CATEGORY
                "STYLE" -> TagCategory.STYLE
                "AUDIENCE" -> TagCategory.AUDIENCE
                "SCENE" -> TagCategory.SCENE
                else -> null
            }
            category?.let { AITag(tagData.name, it) }
        }
        AIAdEnhance(summary = result.summary, tags = tagList)
    } catch (e: Exception) {
        // 4. 解析失败时降级：使用纯文本作为摘要 + 兜底标签
        AIAdEnhance(
            summary = content.take(50),
            tags = listOf(
                AITag("精选推荐", TagCategory.CATEGORY),
                AITag("优质内容", TagCategory.STYLE),
                AITag("广泛受众", TagCategory.AUDIENCE),
                AITag("日常消费", TagCategory.SCENE)
            )
        )
    }
}
```

### 3.7 坑七：Compose Compiler 与 Kotlin 版本匹配

**现象**：各种奇怪的编译错误，但错误信息不直观。

**原因**：Compose Compiler 对 Kotlin 版本有严格的版本对应关系。

**关键规则**（查阅 [Compose Kotlin Compatibility Map](https://developer.android.com/jetpack/androidx/releases/compose-kotlin)）：

| Kotlin 版本 | 推荐 Compose Compiler 版本 |
|------------|---------------------------|
| 1.9.22     | 1.5.10                    |
| 1.9.21     | 1.5.8                     |
| 1.9.20     | 1.5.4                     |
| 1.9.0      | 1.5.2                     |

**正确配置方式**（使用 Version Catalog）：
```toml
[versions]
kotlin = "1.9.22"
composeCompiler = "1.5.10"

[plugins]
android-application = { id = "com.android.application", version = "8.3.2" }
kotlin-android = { id = "org.jetbrains.kotlin.android", version.ref = "kotlin" }
kotlin-serialization = { id = "org.jetbrains.kotlin.plugin.serialization", version.ref = "kotlin" }
hilt = { id = "com.google.dagger.hilt.android", version = "2.51" }
ksp = { id = "com.google.devtools.ksp", version = "1.9.22-1.0.17" }
```

## 6. 结语

**这个项目的最大价值不在于完成了什么功能，而在于：**

1. **建立了对 Compose 声明式 UI 的正确心智模型**
   - 理解 State 驱动 UI 的单向数据流
   - 理解 Side Effect 的正确使用时机
   - 理解 remember/key 与组件生命周期的关系

2. **积累了大量"坑"的经验**
   - 这些问题无法从文档和教程中学到
   - 知道"为什么不能这么做"比"知道怎么做"更重要

3. **形成了架构设计思维**
   - 如何设计可扩展的数据层
   - 如何设计可维护的 UI 组件
   - 如何设计可替换的 AI 服务
   - 如何平衡开发速度与代码质量

4. **理解了移动端 AI 集成的实际挑战**
   - API 成本与响应速度
   - 结果稳定性与降级策略
   - 用户体验与加载时间的权衡
